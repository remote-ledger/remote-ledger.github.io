# Imported from RemoteCentral's Infrared Hex Code Database

Everything under `remotes/remotecentral/` except this file is generated by `rl import remotecentral` from the
snapshot in `sources/remotecentral/`. It is **not authored here**. SPEC.md R19 sets the conditions an import must
meet, and DESIGN.md section 30 describes how this one meets them.

- **Upstream:** RemoteCentral.com's Infrared Hex Code Database (<https://www.remotecentral.com/cgi-bin/codes/>):
  Pronto hex codes that people learned from remotes with a programmable remote and uploaded, listed by brand, by
  device, and under the remote model each was learned from. The site says of it: "Note that some codes may be
  duplicated and/or imperfect learns and this section is provided only as a convenience."
- **Tier:** every key is **Untested**, the lowest tier (SPEC section 5). The source disclaims its own codes and
  nothing here cross-checks them, so they are offered, not confirmed. A key earns a higher tier the way any key
  does: a second source that agrees, or a person who tried it.
- **The pin:** the site is about three thousand pages, so `sources/remotecentral/` holds what the pages say, as
  one gzipped file for each brand (`tools/fetch_remotecentral.py` writes them), and a `MANIFEST.json` with the
  retrieval date and the SHA-256 of each file. The importer refuses a file whose hash differs, and every
  citation names the page of the site, the brand file and the first eight hex digits of its hash.
- **Licence:** none recorded. The site's pages say "All rights reserved" and state no licence for the database.
  The repository treats a table of reference remote codes as facts, which have no licence to record (the
  owner's decision of 2026-10-08, DESIGN D110), and D131 applies that to this site: SPEC section 4 had listed
  Remote Central as excluded by its licence alone, and that line is changed with this import. If the site's
  owners ask for it to be removed, deleting this directory and `sources/remotecentral/` removes every imported
  file.

## What it imports

One file for each page of the database: the model is the page's title without the brand (`AVC-3020`), and
`controls` names the device as the page does. A page's codes are filed by the carrier frequency word of their
Pronto string and by whether it has an intro, as one file holds one carrier (SPEC R3) and one play rule (D78), so
a page whose strings do not all agree has files named `AVC-3020 [38.7 kHz]`. Each code is a `pronto` form, kept
as the page gives it, with no protocol name: what protocol a learned string is, if any, is not decided here. The
remote model the codes were learned from, and the page of the site, are in each key's citation.

A string that is not a Pronto signal is not imported: some uploads write every on-time as `0000`, and some have
a length that is not the one their header gives. `IMPORT.md` counts each kind, with the reason.
