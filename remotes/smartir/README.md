# Imported from the SmartIR codes database

Everything under `remotes/smartir/` except this file and `LICENSE` is
generated by `rl import smartir` from SmartIR's `codes/` database. It is
**not authored here**. SPEC.md R19 sets the conditions an import must meet,
and DESIGN.md §15 describes how this one meets them.

- **Upstream:** <https://github.com/smartHomeHub/SmartIR>. The commit every
  file was built from is named in `IMPORT.md` and in every citation.
- **Licence:** MIT; see `LICENSE`, copied verbatim from upstream
  (`Copyright (c) 2019 Vassilis Panos`). Unlike LIRC's remotes database,
  this one states its licence outright, so there is no reading involved.

## What v1 imports, and what it does not

SmartIR has four categories. Two are genuinely button-shaped --
`media_player` (power, volume, channel, a `sources` map) and `fan` (speed
levels, oscillate) -- and are what this import covers. The other two,
`climate` and `light`, describe a **state matrix** (mode × fan speed ×
temperature, or brightness × colour temperature): dozens to hundreds of
states per file, not a physical remote's buttons. Mapping those onto this
project's `keys` schema would be a real semantic stretch, not a mechanical
one, so v1 leaves them out entirely -- every file in `climate/` and
`light/` is listed in `IMPORT.md` as out of scope, not silently dropped.

Within `media_player`/`fan`, only `supportedController: "Broadlink"`
profiles are imported: a `Base64` command is a Broadlink IR packet,
decoded to a `raw` form; a `Pronto` command is passed through verbatim as
a `pronto` form. Every other controller (`Xiaomi`, `ESPHome`, `LOOKin`,
`MQTT`) is a different, unrelated wire format and is skipped and reported,
not guessed at.

SmartIR itself has no notion of "remote" -- a profile names a
manufacturer, the device model(s) it controls, and nothing else. There is
no remote model number to put in this schema's `model` field. Rather than
inventing one, `model` here is a synthetic designation built from
SmartIR's own catalog id (`"SmartIR media_player 1000"`), and the real
`supportedModels` upstream records go under `controls`, where R2 already
says controlled products belong (DESIGN.md §15, D43).

## What an imported remote is, and is not

- **Every form is `plausible`**: one source that nothing has cross-checked
  (SPEC §5). SmartIR's own data carries no per-code contributor the way
  LIRC's comment headers do, so citations don't carry an attribution
  clause; attribution for the whole database lives here and in `LICENSE`,
  as MIT requires.
- **Each citation says how the form was produced:** either a Broadlink IR
  packet, base64-decoded, or a Broadlink Pronto capture, provided verbatim.
  Neither `carrierHz` nor `minSends` is recorded upstream -- a Broadlink
  capture is protocol-blind -- so both are defaulted (38 kHz, 1 send) and
  the citation says so.
- **A command upstream lists as several redundant captures of the same
  button** (a JSON array instead of one string) imports only the first;
  the citation says how many there were.
- **Authored data wins.** An upstream profile that collides with an
  authored remote is skipped. To curate an imported remote, move its file
  out of this directory: from then on it is authored, and the import
  leaves it alone.
- **Nothing is dropped silently.** `IMPORT.md` lists every category,
  file and button the import could not represent, with the reason.

Do not edit files here by hand; the next import overwrites them.
